# Рекомендательный алгоритм — проект v1

**Статус RJ-05A.** Экспериментальное ядро реализовано и ожидает приёмки. Ниже также описаны будущие возможности интерфейса и AI.
**Принцип утверждён:** AI помогает выделять темы заметки; ранжирование книг выполняется детерминированно и без AI.

## 1. Что алгоритм должен и не должен делать

### Контракт прототипа RJ-05A

`recommend(library, preferences?, candidates?)` принимает записи v0.1 и по умолчанию использует локальный каталог из 33 книг. У каждой карточки есть источник и краткое редакционное обоснование тем. В расчёт входят только темы. Жанры, поджанры, характеристики повествования и настроения имеют отдельные словари.

- В памяти запись может содержать `catalogBookId` и подтверждённые `themeIds`. При отсутствии ID для сопоставления нужны название и автор. Учитываются регистр, внешние и повторяющиеся пробелы и нормализация Unicode. При неоднозначности связь пропускается.
- Вклад оценки берётся из таблицы раздела 3. Для каждой темы к среднему по прочитанным книгам добавляется начальный сигнал из `preferences` (+1 или −1). Отсутствующий сигнал равен нулю. При нескольких оценках одного каталожного произведения прототип использует первую подходящую запись в порядке входной полки.
- Для кандидата сумма весов делится на корень числа его уникальных тем. Нулевые и отрицательные результаты остаются в выдаче. При равенстве баллов порядок задаёт стабильный ID. «В планах» возвращает признак `planned` без прибавки к баллу. Любой исключающий статус того же произведения имеет приоритет.
- Ответ содержит число учтённых книг, режим и список кандидатов. Каждое основание указывает общую тему, её вес, начальный сигнал и записи полки с оценками и происхождением тем. Положительные и отрицательные основания сохраняют знак. При отсутствии совпадений список оснований пуст.
- Если все веса нулевые, режим выдачи — `neutral`. При ненулевом профиле и менее двух учтённых книг — `preliminary`, в остальных случаях — `personalized`. Режим относится ко всей выдаче.

Коэффициенты, состав каталога и поведение для запланированных книг проверяются в рамках открытого решения RJ-OPEN-002. Команда для ручного сравнения оценок приведена в README.

**Должен:** учитывать оценки и выраженные читателем интересы, сортировать непрочитанные книги из ограниченного каталога, объяснять результат доступным языком, работать офлайн, обновляться после изменения оценки или тем.

**Не должен:** обещать прогноз пользовательской оценки 1–10, выдавать совпадение жанра за понимание личности, пересказывать непрочитанную книгу как прочитанную, выдумывать основания для рекомендации или обращаться к AI при каждом открытии списка.

## 2. Два источника данных

### A. Полка читателя

У каждой книги уже есть `id`, `title`, `author`, `genre`, `status`, `rating` (0 означает «без оценки»), `note`. Планируемые дополнительные поля:

- `catalogBookId?` — необязательная ссылка на книгу из рекомендательного каталога;
- `themeIds?` — **подтверждённые пользователем** темы;
- `themeOrigin?` — `manual` или `ai-reviewed`, исключительно для пояснения происхождения;
- `themeAnalysisVersion?` — версия словаря/инструкции AI, если анализ проводился.

Новые поля вводятся **только с миграцией и тестами** старого JSON; точная схема пока не утверждена.

### B. Каталог книг-кандидатов

Для MVP ориентир 30–50 книг. Каждой требуется стабильный ID, название, автор, жанр, набор тематических тегов и короткое пояснение, на каких проверенных характеристиках основаны теги. Данные каталога и пользовательская полка — разные сущности.

Примеры тем для первоначального обсуждения, **не окончательный словарь**:

- `unknown-intelligence` — чуждый/нечеловеческий разум;
- `limits-of-knowledge` — границы человеческого познания;
- `identity` — поиск себя и идентичность;
- `memory` — память и восприятие времени;
- `human-relationships` — человеческие отношения;
- `moral-choice` — моральный выбор;
- `society` — общество и социальная критика;
- `loss` — потеря, одиночество, переживание горя.

Не использовать исключительно жанры: одна книга может объединять философские, психологические и фантастические темы. Для первого релиза утвердить компактный словарь, приблизительно 15–25 тем, и покрыть им весь стартовый каталог.

## 3. Как строим профиль интересов без AI

1. Берём **только** книги со статусом «Прочитано» и оценкой 1–10. Остальные не меняют вес предпочтений.
2. Для каждой такой книги берём подтверждённые темы из полки, а если их нет — известные темы совпавшей книги каталога. Свободную заметку без AI не считаем автоматически понятой.
3. Оценка меняет отношение к темам. Для первого прототипа предлагаем простую таблицу (коэффициенты подлежат проверке):

| Оценка читателя | Вклад темы в профиль |
| --- | ---: |
| 9–10 | +3 |
| 8 | +2 |
| 6–7 | +1 |
| 5 | 0 |
| 4 | −1 |
| 1–3 | −2 |

4. Для каждой темы считаем **средний вклад** среди оценённых книг, которым эта тема присвоена. Это не даёт одной часто встречающейся теме бесконечно увеличивать вес при росте библиотеки.
5. При наличии менее двух оценённых книг показываем, что персонализация пока предварительная, и предлагаем пользователю выбрать интересующие темы вручную. Нельзя делать уверенные выводы по одной оценке.

**Пример:** если читатель высоко оценил «Солярис» и отметил темы `unknown-intelligence`, `limits-of-knowledge`, `identity`, эти темы получают положительный вес. Если позже книга с темой `unknown-intelligence` получит низкую оценку, вес этой темы уменьшится. Жанры могут служить дополнительным слабым признаком, но не главным критерием.

## 4. Как ранжируем кандидатов

Предлагаемая первая формула:

```text
themeScore(candidate) = сумма весов интересов по совпадающим темам
score(candidate) = themeScore(candidate) / sqrt(количество тем кандидата)
```

Деление на корень числа тем сдерживает преимущество книг с чрезмерно большим числом тегов. Формулу и веса необходимо утвердить на примерах перед реализацией, не называть оценку релевантности «вероятной оценкой читателя».

Правила:

- Исключить книги со статусами «Прочитано», «Читаю», «Не интересно» в пользовательской полке.
- Книги «В планах» можно рекомендовать, отмечая, что они уже добавлены в список. Это **предложение** к утверждению.
- Сопоставлять каталог с полкой сначала по `catalogBookId`; при отсутствии — по нормализованной паре «название + автор» с осторожной обработкой неоднозначностей.
- При равных баллах использовать стабильный порядок (например, по каталожному ID), без случайных перестановок при каждом открытии.
- При отсутствии выраженных предпочтений показать нейтральную начальную подборку из каталога и объяснить, что она пока не персональная.
- Всегда показывать причину из реальных совпадений, например: «Подходит по темам границ познания и поиска себя; эти темы вы отмечали после „Соляриса“».
- Не раскрывать внутренний числовой балл как объективную оценку качества книги. Для пользователя достаточно порядка и объяснения.

## 5. Роль AI: анализ только выбранной заметки

**Событие:** пользователь нажал «Определить темы впечатления» у конкретной книги.

1. UI показывает точный текст запроса, который будет передан: название, автор (если выбран), одна заметка. Согласие — отдельное действие.
2. Защищённый серверный маршрут вызывает согласованную модель. API-ключ **никогда не передаётся браузеру**.
3. Модель получает словарь доступных тем и инструкцию: выдели **не более 1–3 тем**, используй факты только из заметки, укажи короткую фразу-основание для каждой, допускай пустой результат.
4. Ответ проверяется по строгой схеме: ID темы существует в словаре, длины и количество полей ограничены, любые неизвестные значения отклоняются.
5. Пользователь видит предложения AI и сам принимает или исправляет их. В профиль интересов попадают **только подтверждённые темы**.
6. Если заметка изменена, прежние темы не должны незаметно считаться подтверждёнными для нового текста; UI предлагает пересмотреть их.
7. Если сервис недоступен, сохранение книги, ручной выбор тем и рекомендации продолжают работать.

**Запрещено:** отправлять в модель всю библиотеку или все заметки без отдельного решения; включать AI-вызов автоматически после каждой клавиши/перезагрузки; показывать выдуманную AI-демонстрацию как живой ответ.

## 6. Прозрачный пример без неподтверждённых оценок

Пользовательское впечатление о «Солярисе»: «Мне интересна идея разумного океана, который не укладывается в человеческое понимание. Попытка узнать чужой разум приводит к попытке понять себя».

Возможный AI-результат:

- `unknown-intelligence` — «разумного океана»;
- `limits-of-knowledge` — «не укладывается в человеческое понимание»;
- `identity` — «попытке понять себя».

Это **тестовый пример**, а не результат вызова реальной модели. Сам пользователь ещё не указал числовую оценку книги: до его оценки эти темы не должны автоматически приобретать положительный вес в модели интересов.

После оценки и подтверждения тем можно сравнивать непрочитанные книги по совпадению тем и объяснять, почему определённый кандидат оказался в топе. Его фактическое место зависит от всего каталога и других оценок пользователя.

## 7. Тесты и пограничные случаи

- Высокая оценка усиливает связанные темы; низкая ослабляет; отсутствие оценки не влияет.
- Изменение оценки или подтверждённых тем изменяет итоговый топ предсказуемым образом.
- Повторные одинаковые входные данные дают один и тот же порядок рекомендаций.
- Прочитанные и отвергнутые книги не попадают в топ.
- Нет совпадающих тем → честное объяснение, почему персонализации мало.
- Ошибка AI, пустая заметка, отказ пользователя отправлять текст не повреждают библиотеку.
- Подозрительный или некорректный ответ модели не сохраняется без проверки.
- Импорт из старой схемы не теряет оценки и впечатления, новые поля получают безопасные значения по умолчанию.
