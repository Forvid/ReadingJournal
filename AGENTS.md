# Правила Codex — Читательский дневник

## Контекст и границы

- Владелец продукта: **Forvid**. Он утверждает задачи, бюджет, публикацию и принимает результат. Отчёты, документация и интерфейс — на русском.
- **ChatGPT** ведёт продуктовые обсуждения и документацию; **Codex** пишет и проверяет код по утверждённым заданиям. Не воспринимай обсуждение идеи как разрешение на реализацию.
- ReadingJournal — отдельный проект. **Не изменяй Stroysite**, другие репозитории и чужие рабочие папки.
- Перед каждой задачей прочитай `README.md`, `docs/PROJECT.md`, `docs/ARCHITECTURE.md`, `docs/RECOMMENDATION_ALGORITHM.md`, `docs/DECISIONS.md` и применимую часть `docs/TEST_PLAN.md`. Проверь состояние рабочей папки и не перезаписывай несвязанные изменения.
- Бери **одну** согласованную задачу за раз. Если решение в документации обозначено как «открыто», не считай его утверждённым.

## Реализовано и запланировано

- Код в исходном архиве — **v0.1**: React, TypeScript, Vite, `localStorage`, импорт/экспорт JSON, CSS, оболочка PWA.
- Гибридное направление утверждено, но **AI-анализ и рекомендации пока отсутствуют в коде**.
- Не добавляй аккаунты, синхронизацию, платные зависимости, отправку пользовательских заметок наружу и публичное развёртывание без отдельного согласования.

## Инженерные правила

1. Сохраняй строгую типизацию, отделяй доменную логику рекомендаций, хранилище и UI.
2. Не ломай существующие записи. Схема резервной копии должна быть версионирована; изменения данных — с явными миграциями и тестами обратной совместимости.
3. Ошибки чтения, валидации или импорта **не должны перезаписывать исходные данные**. Повторный импорт не должен плодить дубликаты одного и того же ID.
4. Для демо используй только вымышленные заметки и тестовые данные; не публикуй реальную библиотеку Forvid по умолчанию.
5. Не записывай API-ключи в клиентский JavaScript, архивы, историю Git или публичные конфигурации. Для запросов AI предусмотрена отдельная защищённая серверная функция.
6. AI вызывается **только после явного действия и подтверждения** пользователя. Перед запросом покажи точный текст отправки: название, автор (если включён) и одну выбранную заметку. Не отправляй всю библиотеку или историю чтения.
7. AI возвращает структурированные темы из согласованного словаря и короткие опорные фразы из заметки. Не выдавай предположения модели о сюжете за факты и не подменяй пользовательскую оценку прогнозом AI. Пользователь может исправить темы.
8. Детерминированные рекомендации должны работать офлайн по сохранённым данным, даже если AI недоступен. Объяснение рекомендации опирается только на известные темы и оценки.
9. При публичном AI-доступе нужны ограничения частоты запросов, контроль объёма текста и расходов, безопасная обработка ошибок и запрет бесконтрольных повторных вызовов.
10. Интерфейс проверяй на настольной и мобильной ширине; для PWA проверяй production-сборку после первого онлайн-открытия.

## Порядок работы с Git

- Для каждой задачи создай отдельную feature-ветку от `main`.
- Перед коммитом проверь состав индекса, запусти проверку типов, тесты и сборку. Создай коммит с сообщением, описывающим результат задачи.
- Отправь feature-ветку в GitHub и открой Draft Pull Request в `main` для проверки Forvid.
- Codex не объединяет PR с `main` самостоятельно. Для force push требуется отдельное разрешение Forvid.

## Завершение задания

- Объясни коротко, что изменено, какие файлы затронуты и почему.
- Предложи Forvid точные шаги ручной проверки; укажи ожидаемый результат и ограничения.
- Выполни `npm run check` и `npm run build`, а `npm test` — когда тестовый скрипт появится. Не заявляй «все тесты пройдены», если они не запускались.
- По возможности добавь автоматические тесты новой доменной логики и регрессий импорта/экспорта.
- Не публикуй сайт, не создавай платные ресурсы и не отправляй данные во внешние сервисы как часть проверки без отдельного разрешения Forvid.
